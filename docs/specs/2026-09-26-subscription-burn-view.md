# 구독 지출·한도 소진 전망 (L)

- Intent: docs/intents/2026-09-26-subscription-burn-view.md

Goal: 메뉴바 대시보드가 "이 구독들에 월 얼마가 나가고, 각 서비스가 주간 한도를 다 쓰는가"를 한 화면에서 답해, 구독을 늘릴지 줄일지 판단할 수 있게 한다.

Non-goals: 결제·청구 시스템 연동(단가는 사람이 설정 파일에 적는다). 계정 자동 생성·해지. 요청 단위 과금 추적. 프록시(teamclaude/teamcodex) 저장소 수정. 사용량을 조절하는 어떤 자동 동작도 하지 않는다(보여주기만 한다).

Acceptance:
- 지출 블록이 월 합계와 "돈은 나가는데 기여하지 않는 계정 수"를 오류/의도적 비활성으로 나누어 보인다.
- 소진 블록이 서비스 4종(Claude·Codex·agy·Grok)별로 계정 수(지불/기여)·월 지출·주간 소진 전망·판정을 한 행씩 보인다.
- 단가가 설정되지 않은 서비스는 금액 자리에 `미입력`을 표시하고, 어떤 추정 금액도 만들지 않는다.
- 이력이 2주기 미만이면 전망에 `추정` 배지가 붙고, 2주기 이상이면 과거 주기 평균과 최소~최대 범위를 표시한다.
- 주기 중 가용 계정 0이 관측된 서비스는 전망과 무관하게 `부족`으로 판정한다.
- 리셋 시각이 없는 Grok은 이력이 쌓이기 전까지 `수집 중`으로 표시하고 전망을 지어내지 않는다.
- 데몬이 꺼진 사이 넘어간 주기는 `불완전`으로 표시하고 평균 계산에서 제외한다.

Test: 순수 함수(전망·판정·필요 계정 수·주기 경계 감지)는 Swift 단위 테스트. 화면 배선은 `test_dashboard_wiring.py`(러너와 같은 `python3 <파일>` 실행 경로). 지출 미입력·이력 0주·가용 0·불완전 주기·Grok 수집 중 다섯 가지 빈 상태를 스냅샷 픽스처로 각각 렌더해 눈으로 확인한다. 실패 화면을 스냅샷에 넣지 않으면 확인된 적 없는 화면이 된다(2026-09-24 실측).

Plan: 1 이력 저장(주기 경계 감지·스키마) → 2 전망·판정 순수 함수 → 3 설정 파일(단가) → 4 화면 두 블록 → 5 빈 상태 픽스처·렌더 검증 → 6 교차 벤더 적대 검토.

## 1. 왜 이 화면인가 (설계 시점 실측)

네 레인을 실측한 값이 설계를 결정했다.

| 레인 | 계정 | 가용 | 주간 사용 | 세션(5h) | 리셋 시각 |
|---|---|---|---|---|---|
| Claude | 17 | 3 | 평균 82%, 90%+ 8개 | 11% | 있음 |
| Codex | 7 | 3 | 평균 73%, 최대 100% | 0% | 있음 |
| agy | 1 | — | 6% | 0% | 있음 |
| Grok | 1 | — | 29% | — | **없음** |

세 가지가 읽힌다.

**주간이 병목이고 세션은 비어 있다.** Claude 주간 82% 대 세션 11%. 세션으로 판정하면 "한참 여유"라는 틀린 답이 나온다. 그래서 판정은 두 창 중 높은 쪽으로 한다.

**계정 17개 중 10개가 기여하지 않는다.** 오류 6 + 비활성 4. 돈은 17개분 나간다. 이 사실을 분리해 보이지 않으면 "구독을 더 할까"에 잘못 답한다. 고칠 수 있는 문제에 돈을 쓰게 된다.

**agy는 6%만 쓴다.** 단일 구독이라 계정 수 조정이 아니라 다운그레이드·취소 판단 대상이다.

## 2. 목표 사용률은 100%다

소유자가 정한 목표다. 주간 한도를 남기지 않고 다 쓰는 것이 이 풀의 운영 목표다.

그 선택의 대가를 화면이 숨기지 않는다. **평균을 100%에 맞추면 평균보다 많이 쓴 주에는 막힌다.** 그래서 이력이 쌓이면 평균만이 아니라 최소~최대 범위를 함께 보인다. "평균 100%"가 "매주 딱 맞다"로 읽히지 않게 한다.

목표가 100%이므로 **"부족"의 정의가 달라진다.** 100% 도달은 실패가 아니라 목표 달성이다. 진짜 부족은 한도 때문에 실제로 일이 막힌 것이고, 그것은 추정이 아니라 관측할 수 있다. 가용 계정이 0이 된 순간이다.

## 3. 무엇을 쌓는가

### 3.1 주기 단위 요약만 쌓는다

60초 폴링 값을 모두 쌓을 이유가 없다. 판정에 필요한 것은 "지난 주기에 실제로 몇 % 썼나" 하나다.

리셋 시각이 바뀌는 순간이 주기가 넘어간 순간이다. 그때 직전 주기를 확정해 한 줄 남긴다.

```
{
  "version": 1,
  "cycles": [
    {
      "lane": "claude",          // claude | codex | agy | grok
      "window": "7d",            // 7d | 5h
      "endedAt": "2026-09-22T00:00:00Z",
      "contributing": 7,          // 그 주기에 기여한 계정 수 (분모)
      "paid": 17,                 // 그 주기에 돈이 나간 계정 수
      "meanUtilization": 0.82,
      "maxUtilization": 1.0,
      "exhaustedAccounts": 8,     // 100% 도달 계정 수
      "blockedMoments": 3,        // 가용 0이 관측된 횟수
      "complete": true            // 데몬이 주기 내내 살아 있었는가
    }
  ]
}
```

저장 위치는 기존 세션 통계 캐시와 같은 디렉터리(`~/.codex/cache/`)에 `cc-menubar-quota-history-v1.json`. 주당 레인별 한 줄이라 8주치가 40행 남짓이다. 보관은 레인·창 조합마다 최근 32개까지이고, 넘으면 오래된 것부터 버린다.

### 3.2 분모를 반드시 함께 남긴다

계정 7개가 살아 있을 때의 82%와 15개일 때의 82%는 소비량이 두 배 차이다. `contributing`을 같이 적지 않으면 "지난주보다 많이 썼다"가 성립하지 않는다. 이 필드가 빠지면 이력 전체가 비교 불가능해진다.

`paid`를 따로 적는 이유는 지출 대비 기여를 과거 시점에도 볼 수 있게 하기 위해서다.

### 3.3 주기 경계를 어떻게 아는가

| 레인 | 방법 |
|---|---|
| Claude · Codex | `unified7dReset` / `unified5hReset` 값이 바뀌면 주기 전환 |
| agy | 버킷의 `reset_time`이 바뀌면 전환 |
| Grok | 리셋 시각이 없다. **사용률이 크게 떨어지는 순간**을 경계로 역산한다 |

Grok의 역산은 새 발명이 아니다. 이 저장소의 힉스필드 크레딧이 이미 같은 일을 한다. 거래 내역에서 갱신일을 역산하고, 추정이라는 사실을 화면이 숨기지 않는다(`HiggsfieldCredits.swift`). 같은 자세를 따른다: 경계가 확정되기 전에는 `수집 중`이고, 확정 후에도 추정임을 표시한다.

하락 판정 기준은 **직전 관측 대비 20%p 이상 하락**이다. 사용률은 단조 증가하다 리셋에서만 떨어지므로, 잡음이 아닌 하락은 리셋이다. 20%p는 관측 간격(60초) 동안 정상 사용으로 도달하기 어려운 폭이다.

### 3.4 데몬이 꺼져 있던 주기

`complete: false`로 남기고 평균 계산에서 제외한다. 마지막 관측값은 "최소 추정"으로 보관하되 판정에는 쓰지 않는다. 구멍을 메우려고 값을 지어내지 않는다.

## 4. 전망 계산

```
경과율 = (주기 길이 − 리셋까지 남은 시간) ÷ 주기 길이
```

| 조건 | 계산 | 표시 |
|---|---|---|
| 완료 주기 2개 이상 | 과거 주기 `meanUtilization` 평균 | `최근 N주 평균 88% · 61~97%` |
| 이력 부족 | 현재 사용률 ÷ 경과율 | `82% → 100%+ 추정` |
| 경과율 < 30% | 같은 외삽 | `추정 · 신뢰 낮음` |
| 경계 미확정(Grok) | — | `수집 중` |

이력이 쌓이면 표시가 자동으로 바뀐다. 사람이 전환 버튼을 누르지 않는다.

## 5. 판정 정책

### 5.1 어떤 창으로 판정하는가

주간과 세션 중 **사용률이 높은 쪽**으로 판정한다. 병목이 판정을 지배해야 한다.

### 5.2 판정 기준

| 신호 | 판정 | 색 |
|---|---|---|
| 주기 중 `blockedMoments > 0` | **부족** | 적 |
| 전망 ≥ 100%, 막힘 없음 | 목표 달성 | 녹 |
| 85% ~ 100% | 근접 | 녹 |
| 60% ~ 85% | 여유 | 회 |
| < 60% | 과다 | 황 |

색은 기존 팔레트 의미를 그대로 쓴다(녹=정상, 황=주의, 적=오류, 회=중립). 새 색을 만들지 않는다. `과다`가 황인 이유는 돈이 새는 상태라 주의가 필요하기 때문이고, `여유`가 회인 이유는 당장 할 일이 없기 때문이다.

### 5.3 권고

풀(Claude·Codex)과 단일 구독(agy·Grok)의 답이 다르다.

```
필요 계정 ≈ 기여 계정 × 평균 사용률 ÷ 목표 사용률(1.0)
```

| 레인 | 실측 | 계산 | 권고 |
|---|---|---|---|
| Codex | 7 기여 · 73% | 7 × 0.73 ≈ 5 | 2개 줄일 여지 |
| Claude | 7 기여 · 82% | 7 × 0.82 ≈ 6 | 기여분 기준 1개 여유 |
| agy | 1 · 6% | — | 다운그레이드 검토 |
| Grok | 1 · 29% | — | 이력 수집 후 판단 |

**권고는 순서를 지킨다.** 기여하지 않는 계정이 있으면 그것을 먼저 말하고, 계정 수 조정은 그다음이다. Claude는 오류 6개를 살리면 기여가 13개가 되어 사용률이 절반 아래로 떨어진다. 그때는 "여유"가 아니라 "과다"가 된다. 순서를 뒤집으면 고칠 수 있는 문제에 돈을 쓰게 된다.

## 6. 단가 설정

사람이 편집하는 파일이므로 캐시 디렉터리가 아니라 설정 디렉터리에 둔다: `~/.config/cc-menubar-subscriptions.json`.

```
{
  "version": 1,
  "currency": "KRW",
  "lanes": {
    "claude": { "plan": "Max 20x", "monthly": 0 },
    "codex":  { "plan": "Pro",     "monthly": 0 },
    "agy":    { "plan": "Ultra",   "monthly": 0 },
    "grok":   { "plan": "SuperGrok", "monthly": 0 }
  }
}
```

- `monthly`는 **계정 1개당** 월 금액이다. 서비스 합계 = `monthly × 지불 계정 수`.
- 계정 수는 프록시 status에서 읽는다. 사람이 다시 세지 않는다.
- 파일이 없거나 `monthly`가 0이면 `미입력`으로 표시한다. **어떤 경우에도 금액을 추정하지 않는다.**
- 읽기는 mtime 기반 캐시를 쓴다(2026-09-24에 같은 이유로 도입한 `AccountSubscriptionFileCache` 재사용). 표가 1초 주기로 갱신되므로 캐시 없이는 초당 파일 읽기가 반복된다.

계정별 요금제가 다른 경우는 이번 범위 밖이다. 필요해지면 기존 계정별 구독 기록 기능으로 예외를 덮어쓰는 방식을 얹는다(§10 열린 질문).

## 7. 화면

대시보드 맨 위, 한 줄 요약 밴드 아래에 새 섹션으로 둔다. 폭 880pt.

```
┌ 구독 지출 ───────────────────────────────────────────┐
│  월 합계   미입력                기여 없는 계정  10 / 25   │
│  오류 6 · 복구 가능        꺼 둠 4 · 결정 필요            │
└──────────────────────────────────────────────────┘
┌ 한도 소진 ───────────────────────────────────────────┐
│  서비스    계정      월 지출     주간 소진            판정   │
│  Claude   17 (7)    미입력     82% → 100%+  추정    달성   │
│  Codex     7 (7)    미입력     73% →  91%   추정    근접   │
│  agy       1        미입력      6% →   8%   추정    과다   │
│  Grok      1        미입력     29%          수집 중    —    │
│                                                      │
│  오류 6개 재인증이 먼저 · agy 다운그레이드 검토            │
└──────────────────────────────────────────────────┘
```

**두 블록이 겹치지 않는다.** 위는 합계와 새는 돈, 아래는 서비스별이다. 서비스 이름을 두 번 적지 않는다.

위 예시는 설계 시점 실측 상태다. Claude는 목표대로 주간을 다 쓰고 있지만 그것을 **계정 7개로** 하고 있고, 나머지 10개는 돈만 나간다. 판정은 `달성`이면서 권고는 `오류 6개 재인증이 먼저`인 이유가 이것이다.

**`17 (7)`은 지불 계정과 기여 계정이다.** 이 둘이 다른 것이 현재 가장 중요한 사실이라 붙여 둔다.

**권고 줄은 문제가 있을 때만 그린다.** 모든 레인이 정상이면 그 줄이 없다. 행마다 같은 문구를 반복하지 않는 것은 이 대시보드의 기존 규율이다(2026-09-24 정리).

높이 비용은 약 240pt다(1170 → 약 1410pt).

## 9. 파일 구조

| 파일 | 책임 |
|---|---|
| `menubar/Sources/QuotaHistory.swift` (신규) | 주기 경계 감지·스키마·읽기/쓰기·보관 기간 |
| `menubar/Sources/BurnProjection.swift` (신규) | 전망 계산·신뢰도 (순수 함수) |
| `menubar/Sources/SubscriptionPolicy.swift` (신규) | 판정·필요 계정 수·권고 순서 (순수 함수) |
| `menubar/Sources/SubscriptionRates.swift` (신규) | 단가 설정 읽기(mtime 캐시) |
| `menubar/Sources/SubscriptionBurnView.swift` (신규) | 두 블록 그리기 |
| `menubar/Sources/main.swift` | 섹션 등록·폴링 훅·높이 계산 |

계산을 뷰에서 분리하는 이유는 단위 테스트 때문이다. `main.swift`는 `-parse-as-library` 테스트 바이너리에 들어가지 못하므로, 판정 로직이 거기 있으면 테스트할 수 없다.

## 10. 열린 질문

- **계정별 요금제 차이**: 지금은 서비스 단가 하나를 모든 계정에 곱한다. 실제로 Max 20×와 Pro가 섞여 있다면 합계가 틀린다. 필요해지면 기존 계정별 구독 기록으로 예외만 덮어쓰는 방식을 얹는다.
- **세션(5h) 창의 이력**: 지금 설계는 주간 판정이 주목적이라 5h 이력도 쌓되 화면에는 쓰지 않는다. 세션이 병목이 되는 날이 오면 같은 이력으로 바로 판정할 수 있다.
- **단가 실제 값**: 소유자가 입력하기 전까지 지출 블록은 `미입력`으로 동작한다. 소진 블록은 단가와 무관하게 완전히 동작한다.

## 11. 롤아웃·되돌리기

기존 화면을 바꾸지 않고 섹션 하나를 더한다. 문제가 있으면 섹션 등록만 되돌리면 나머지 화면은 영향을 받지 않는다. 이력 파일은 읽기 실패 시 빈 이력으로 취급하고 화면은 `추정`으로 떨어진다. 파일이 깨져도 앱이 죽지 않는다.
